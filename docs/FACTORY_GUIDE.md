# Выпуск сайтов из шаблона

Обычный ChatGPT перед любой сборкой сначала читает [`../START_HERE.md`](../START_HERE.md), затем [`../RULES.md`](../RULES.md). Входные данные самостоятельно собираются из переданных ссылок, чата и приложений по [`INPUT_CHECKLIST.md`](INPUT_CHECKLIST.md). `AGENTS.md` является дополнительной точкой входа для Codex.

Шаблон готовится к новому салону заменой данных и медиа. Утверждённые компоненты, разметку карточек услуг и стили менять не нужно.

## Вход из TANEM Exporter

Если результат экспортёра уже загружен в `intake/yandex/`, агент сначала работает с ним, а не повторно собирает ту же информацию вручную:

- `business.json` — основной машинный источник;
- `business.txt` — вторичная человекочитаемая копия;
- `assets/` — реальные фотографии;
- `ПРОВЕРКА.html` — только ручная сверка.

Диагностика (`export.log`, `debug/`) и любые секреты в клиентский репозиторий не переносятся. После чтения intake агент открывает внешние источники только для обязательных пробелов или конфликтов. Подробная структура находится в `../intake/README.md`.

## Единственный источник данных

Клиентские данные находятся в `site-data.js`. Один и тот же объект используется desktop- и mobile-версиями. **Для нового салона начните с `site-data.blank.js`**: скопируйте его поверх `site-data.js`, после чего заполните только реальные данные. Демонстрационные услуги нужны исключительно для проверки дизайна основного шаблона, никогда не переносите их клиентам. Перед выпуском обязательно установите:

```js
mode: 'production'
```

Заполняйте только языки, обязательные для страны:

```js
// Россия
country: 'RU',
locales: ['ru', 'en']

// Армения
country: 'AM',
locales: ['ru', 'en', 'hy']
```

Для `RU` запрещено добавлять HY «на всякий случай». Код также поддерживает `UZ → ru/en/uz` и `TJ → ru/en/tg`, но эти режимы используются только по прямому указанию пользователя.

### Адрес и карты

- `salon.city` — короткая строка для интерфейса, например `г. Балашиха`.
- `salon.address` — короткая строка без административных повторов, например `Павлино, 69`.
- `salon.fullAddress` — полный проверенный почтовый/административный адрес; он не выводится целиком в hero.
- `contacts.mapUrl` и `contacts.mapEmbedUrl` обязательны в production.
- `country: 'RU'` использует Яндекс Карты; все остальные поддерживаемые страны используют Google Maps.
- Если `messengerUrl` пуст, карточка мессенджера не создаётся. Если ссылка есть, `messengerLabel` содержит название платформы, например `Telegram`, `WhatsApp`, `MAX` или `Viber`. Телефон также не является заглушкой: при пустом `contacts.phone` телефонные карточки/кнопки не показываются, а маршрут занимает освободившееся место.

## Порядок производства

1. Выполните исследование всех переданных источников по `START_HERE.md` и `INPUT_CHECKLIST.md`.
2. Одним сообщением запросите все недостающие обязательные данные и разрешение конфликтов; не заставляйте пользователя повторно заполнять форму.
3. После получения ответа скопируйте `site-data.blank.js` поверх `site-data.js`.
4. Определите страну и языки, затем заполните только подтверждённые факты. Сразу разделите полный адрес на короткие `salon.city` / `salon.address` для интерфейса и `salon.fullAddress`, а карту подключите по правилу страны.
5. Сохраните утверждённые универсальные `salon.heroDescription` и `salon.about` из `site-data.blank.js` без изменений.
6. Перенесите услуги в `services`: одна реальная услуга — один объект; варианты одной услуги остаются в `variants`.
7. Подключите медиа по `RULES.md`, запись и контакты — только по настоящим ссылкам.
8. Если нет команды или отзывов, оставьте `team` / `reviews` пустыми. Пустой `team` автоматически даёт четыре системные нейтральные карточки «Мастер», а пустые отзывы — нейтральное состояние. Не записывайте эти системные карточки как реальных людей.
9. Проверьте сайт локально на desktop и mobile, затем установите `mode: 'production'`.
10. Выполните все проверки из раздела «Проверка перед выпуском» и публикуйте только по прямому поручению.

Обязательные блоки для production:

- `salon` — название, тип, короткие `city`/`address`, полный `fullAddress`, утверждённые тексты;
- `schedule` — часовой пояс и интервалы работы;
- `contacts` — хотя бы один реальный способ записи, обязательные `mapUrl` и `mapEmbedUrl`; мессенджер только при реальной ссылке;
- `media` — обязательные `hero.webp`, `profile.webp` и галерея; логотип — только если реально есть;
- `categoryLabels`, `categoryOrder`, `services` — каталог услуг;
- `rating` — реальное значение либо `null` и количество оценок;
- `team`, `reviews`, `portfolio`, `gallery` — реальные массивы либо пустые массивы.

Пустые `team` и `reviews` не скрываются. Пустой `team` визуально показывает четыре системные карточки «Мастер», которые не являются данными; пустые отзывы показывают нейтральное состояние. Не заполняйте массивы выдуманными мастерами или отзывами. Остальные необязательные возможности могут скрываться по правилам шаблона.

## Карточка услуги

Один объект в `services` всегда создаёт одну карточку услуги на desktop и mobile. Существующую логику карточки не меняйте.

```js
{
  id: 'haircut',
  category: 'Волосы',
  title: {ru: 'Стрижка', en: 'Haircut'},
  price: '12 000 ֏',
  duration: '1 ч',
  description: {ru: 'Стрижка с консультацией.', en: 'Haircut with consultation.'},
  variants: []
}
```

Правила:

- `id` уникален и не меняется после публикации;
- `category` должна присутствовать и в `categoryLabels`, и в `categoryOrder`;
- `price`, `duration` и `description` можно оставить пустыми — карточка сохранит штатную механику записи;
- длинное описание автоматически получает «Подробнее» по утверждённой логике;
- диапазон цены записывается как `18 000–30 000 ֏`;
- варианты услуги задаются объектами `{label, duration, price}` в `variants`;
- нельзя копировать карточку вручную в `desktop.js` или `mobile.js`.

Зафиксированный контракт дизайна подробно описан в `docs/SERVICES_STYLE_LOCK_V1.md`. На мобильном устройстве запрещено переносить название категории услуг на вторую строку или уменьшать шрифт. Ровно две категории равномерно делят доступную ширину; при любом другом количестве используется естественная ширина и горизонтальная прокрутка, если она нужна. Категории мобильной галереи находятся на однотонном фоне, а последняя вкладка карточки мастера полностью прокручивается в видимую область.

## Медиа и ссылки

Канонический контракт медиа находится в [`RULES.md`](../RULES.md). Для нового сайта:

- `hero.webp` → главное изображение салона на mobile и desktop;
- `profile.webp` → фотография блока «О салоне»;
- `gallery-01.webp` ... `gallery-25.webp` → реальные фотографии, которые ChatGPT распределяет по подходящим категориям;
- `team-01.webp` ... → фотография конкретного мастера только вместе с его реальными данными;
- `logo.*` → необязательный прозрачный клиентский логотип;
- `favicon-source.png` → встроенная системная иконка TANEM; технический специалист её не готовит.

В `site-data.js`:
- `media.hero[0]` указывает на `hero.webp`;
- `media.about` указывает на `profile.webp`;
- `media.portfolio` и `media.gallery` используют `gallery-XX.webp`;
- `team[].photo` указывает на соответствующий `team-XX.webp`.

Отдельного desktop-hero больше нет. Один и тот же `hero.webp` используется на мобильной и ПК-версиях.

Локальные файлы кладите в клиентский репозиторий и указывайте безопасным относительным путём. Один и тот же файл галереи можно ссылочно использовать и в `media.portfolio`, и в нужной группе `media.gallery`; физические дубликаты не нужны.

Внешние изображения и ссылки используют `https://`. Не оставляйте `logo-placeholder.svg`, `media-placeholder.svg`, `#` вместо реальной ссылки или демонстрационные записи. Отзывы, если они используются, должны быть только с рейтингом `5`. Текст реального отзыва не переписывается ради красоты; перевод добавляется отдельно, если он требуется языковой конфигурацией сайта.

## Проверка перед выпуском

Из корня проекта запустите:

```bash
node tests/validate-site-data.cjs --production
node tests/check-factory-contract.cjs
node tests/check-template-regression.cjs
```

После push дождитесь всех проверок GitHub Actions:

- схема данных и блокираторы выпуска;
- неизменность утверждённой карточки услуг и CSS-каскада;
- сравнение с эталоном в Chromium и WebKit;
- production-сценарий на desktop, mobile и широком touch-устройстве.

Публиковать сайт можно только после зелёного результата всех проверок.

## Автопубликация GitHub Pages

Клиентские репозитории используют `GitHub Actions` как источник публикации. Не выбирайте `Deploy from a branch`: перед выпуском сайт должен пройти production-валидацию и собраться в безопасный Pages artifact.

Workflow `.github/workflows/pages.yml` при push в `main`:

1. проверяет, что `site-data.js` находится в `mode: 'production'`;
2. запускает production-валидацию и factory/regression checks;
3. собирает только файлы готового сайта в `_site`;
4. исключает `intake/`, `tests/`, `docs/`, `.github/` и другие производственные файлы из опубликованного artifact;
5. публикует artifact через GitHub Pages.

### Первичное включение Pages

Предпочтительный фабричный режим — один организационный секрет `TANEM_PAGES_TOKEN`, доступный клиентским репозиториям. Workflow передаёт его в `actions/configure-pages` с автоматическим enablement, поэтому новый репозиторий может включить Pages сам при первом production-push.

Токен должен иметь право управлять Pages: для classic PAT — подходящий `repo` scope; для fine-grained token/GitHub App — необходимые `Pages: write` и `Administration: write` разрешения на клиентские репозитории.

Если `TANEM_PAGES_TOKEN` не настроен, Pages включается один раз вручную: `Settings → Pages → Build and deployment → Source → GitHub Actions`. После этого все дальнейшие push в `main` публикуются автоматически.

## Новый клиентский репозиторий

Создайте **пустой** GitHub-репозиторий без автоматически созданного README. Самый безопасный путь — клонировать утверждённую release-ветку шаблона с историей, а затем сменить адрес удалённого репозитория:

```bash
git clone --branch salons-v1-production --single-branch https://github.com/ichAEY/Shablon-only-for-salons.git CLIENT
cd CLIENT
cp site-data.blank.js site-data.js
# Заполните site-data.js и добавьте реальные изображения
# Затем поменяйте mode на production
node tests/validate-site-data.cjs --production
git remote set-url origin https://github.com/OWNER/NEW_CLIENT_REPO.git
git add site-data.js
git commit -m "Create salon from approved TANEM template"
git push -u origin salons-v1-production:main
```

В команде `git add` укажите также реальные фотографии, логотип и остальные новые файлы. Если скопировали файлы без истории, GitHub Actions автоматически получает контрольный коммит утверждённого шаблона из исходного репозитория.

**Проверка перед отправкой клиенту:** статус всех GitHub Actions зелёный; в продакшене реальные названия и фотографии на всех языках выбранной страны; короткий адрес без повторов; правильная карта по стране; услуги и цены на ПК/телефоне; связь и запись; отсутствующий мессенджер не создаёт пустой карточки. В клиентском репозитории CI сравнивает исходную разметку услуг и CSS с эталоном, а браузер открывает уже заполненный сайт.

### Галерея и просмотр фотографии (мобильная/ПК)

Мобильная рамка ленты категорий берётся по мотивам Эсмеральды (14 px), но внешняя полоса остаётся точно в цвет основного фона галереи. Кнопки и названия категорий не сжимаются. Мобильная кнопка «Открыть галерею» в предпросмотре **из портфолио** и счётчик располагаются на одной линии ниже изображения, а на ПК счётчик вынесен к правому краю и кнопка шире. Подробности и исключения — в `RULES.md`.


**Категории услуг на телефоне:** шрифт Manrope 13,98 px/500, высота 35 px, боковые отступы 15 px, зазор 8 px. Ровно две реальные категории растягиваются равномерно на доступную ширину. При любом другом количестве карточки сохраняют естественную ширину и при необходимости прокручиваются горизонтально. Начало первой категории остаётся на одной линии с первой карточкой услуги. Не путать этот блок с категориями полноэкранной галереи: их рамку/шрифт не менять.
